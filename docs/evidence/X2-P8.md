## Implemented behavior

An authenticated merchant owner can create an application for an owned merchant or establish their own merchant account, edit a versioned draft, attach up to two private normalized images, and submit. Staff cannot impersonate an owner. Reviewers with native MFA claim minimal queue entries before reading private details/evidence. Needs-information/resubmission preserves submission snapshots; approval/rejection requires fresh authority, the current version, confirmation, reason and audit. Duplicate-name signals remain advisory.

Approval selects an immutable development policy and issues a referenced invoice before a shop exists. A separately scoped finance operator compares the invoice reference, currency, amount and unique external receipt, then records a verified development payment or waiver. Partial credits do not provision. Full settlement atomically finalizes coverage, allocates capacity, creates an immutable shop identity with unpublished design state and active tenancy, and commits audit/notification work. Concurrent/repeated commands cannot double-credit or double-provision. Stable command keys support retry after an uncertain response; changing the payload conflicts. SQL constraints also reject invalid workflow credits.

Corrections append linked negative events, retaining the original credit. Reversal into arrears closes public eligibility without deleting catalogue/design/history. Reconciliation of the outstanding amount restores eligibility within the original coverage, preserving any moderation suspension. Renewal creates one open obligation at a time and finalizes the next period only on full settlement. Grace boundaries, overdue notices and stale/repeated jobs use canonical state under merchant serialization. Only new P8 contracts are automatically scheduled; historical fixture tenancies are unchanged.

Shopkeeper has application, private evidence, invoice and rent/renewal pages. Landlord has scoped application review and development reconciliation/reversal pages. Policy versions can be created through the protected API; there is no policy editor UI yet. The current local operator receives finance permission only through explicit guarded `npm run db:p8`, after migration and identity verification; ordinary seed defaults remain unchanged.
