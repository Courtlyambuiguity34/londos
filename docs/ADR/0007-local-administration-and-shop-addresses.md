# ADR-0007: local administration and stable shop addresses

P8 administrative contract, 2026-10-05. Continue the owner-selected development rent policy and disabled live collection from ADR-0006. This packet completes local team controls, shop-address changes, occupancy/exception views, mall reassignment and administrative pause/resume. Live moderation rules, financial arrangements and production deployment remain separate gates.

An owner with fresh current authentication reads/manages a merchant team. Existing membership/invitation/ownership services remain authoritative; new UI commands additionally compare a merchant revision after acquiring the shared merchant lock. Every team mutation, including invitation acceptance and legacy commands, advances that revision. Concurrent stale commands conflict. Membership and per-shop grants are both required for staff. Demotion/revocation preserves the last-owner constraint and permanently revokes invitations issued by the former owner. Tokens travel only through private notification delivery and a password input on the acceptance form, never a URL or a team-list response. Lists are bounded and paginated.

Shop addresses require current owner authority, fresh authentication, reason, explicit confirmation and the current shop version. Immutable identifiers retain their existing meaning. Each former slug remains permanently reserved to its shop, including while private/closed. A database trigger maintains the address registry for all shop inserts/changes and prevents alias takeover even through direct SQL. Public address resolution still checks current publication, tenancy, moderation and operational eligibility before redirecting to the current canonical path. A redirect never discloses an ineligible shop. UUID-shaped new slugs are rejected to keep immutable-ID routing unambiguous.

A separate `operations` operator permission requires native MFA. Minimal shop queues and aggregate mall occupancy need that permission; private operational details/commands additionally require an explicitly claimed, audited shop scope. Claiming requires fresh MFA and a reason. Self-claim/administration is denied for active merchant members. Claims do not grant application-finance scope. Financial exception views require finance permission and application-finance scope. Default seeds do not acquire operations permission; an explicit guarded development command enables only the known fictional review operator.

Mall reassignment serializes on the merchant and the same global capacity lock used by initial provisioning, rechecks current authority after waits, compares the shop version and refuses a full target mall. It preserves immutable shop identity, slug/history, tenant ownership, catalogue, design, moderation, rent contract and discovery ranking. Occupancy is an operational planning count, not production capacity proof. New mall creation at the configured threshold remains the existing provisioning behavior.

Administrative pause is an independent canonical operational hold. Resume removes only that hold; it never credits an invoice, rewrites tenancy dates, publishes a draft or lifts moderation. All public eligibility consumers—including contacts, search and ready images—check the hold. Merchant publication and stale rent jobs cannot bypass it. Pause/resume needs fresh operations authority, scope, reason, confirmation and version; canonical state and append-only audit commit atomically. This supports reversible operator recovery without inventing a financial grace extension or live moderation policy.

Verification must cover two merchants, constrained staff, current and revoked scopes, stale versions, racing capacity allocation, alias takeover/resolution, last-owner safety, invitation token privacy, and paused public shop/search/contact/media behavior. Local functional/browser evidence and migration preservation are required before marking the packet complete.
