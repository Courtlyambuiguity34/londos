# ADR-0011: local governed exports, retention holds and limited erasure

P9.8 development packet, 2026-10-06, Africa/Kampala. Preserve applied migrations and all completed financial, trust, incident and analytics contracts. This is fictional loopback functionality; no live legal retention policy or identity adjudication is invented.

Fresh current merchant owners can download bounded sections of their business data and request reviewed erasure. Exports allowlist fields, paginate by canonical UUID, disclose omitted categories and never include authentication secrets, other members' identities, customer enquiry contacts/messages, third-party reports, private investigation notes, evidence bytes, notification/job payloads or raw analytics receipts. Own application profiles and original-reporter incident messages are separately limited to the requesting user. Financial records retain their current authorized business meaning. A section is a current serialized read, not a durable whole-account snapshot or a complete legal subject-access response. Downloads are private, audit only section/count metadata and create no stored export artifact or bearer URL.

A new explicit privacy permission, native fresh MFA, exclusive case assignment, separate privacy scope and no active merchant self-membership govern operator review. Neither analytics, support, finance nor moderation grants implicit privacy authority. Owner-visible explanations are separate from private review/hold reasons. Commands compare versions after merchant serialization and append immutable history. Request retry identity is immutable and hashed; changed retries conflict. Retention holds target an exact merchant/resource and require reasoned release. Holds block erasure, not legitimate owner exports. Holds survive cancellation, denial and released assignment. Reasoned unassignment clears approval; revoked grant/scope permits explicit qualified re-claim into a new scope.

The immutable development policy permits only manually reviewed erasure; there is no automatic bulk timer or closure-triggered deletion. Eligible closed enquiries and rejected-application evidence require at least 30 days since closure/rejection. Older enquiries lacking a reliable closure time start their retention clock at migration. All eligible effects still require an explicit local erasure flag, current approval and final checks. Approved/financially referenced applications, private trust/incident/contact/audit history, financial ledgers and native accounts are retained under this policy. Requests for protected history receive an explicit retained outcome rather than a false deletion claim.

Enquiry erasure removes name, reply address and message from the primary record, retaining minimal identity/status/retry fingerprint so retries cannot recreate erased content. Erasure is one-way. Rejected-application erasure removes only verification byte payloads; canonical application/submission/audit metadata remains intact. Shop analytics erasure removes that shop's retained daily metrics and permanently stops future capture for it; platform counts and audit-derived merchant activity remain separate. Analytics capture shares merchant serialization so an in-flight observation cannot recreate erased shop counts. Existing analytics expiry/dedupe rules remain unchanged.

Approval binds a current native session, exact target plan and a five-minute deadline. A durable job contains only case identity/version. The worker locks the merchant and its own current lease, rechecks requester ownership, operator privacy grant/session/MFA/scope/assignment, holds, policy, deadline and target fingerprint before effects. Expired/revoked/changed plans return to review; no effect is applied. Completion, audit/history and job-effect dedupe commit with the SQL erasure. SQL guards require the exact governed approved context before enquiry scrub, verification-byte deletion or permanent capture exclusion. Stale/retried workers cannot repeat or widen it. A disabled worker/flag leaves execution incomplete and visible.

“Primary-data erasure completed” describes only verified SQL effects. Database backups/WAL, platform snapshots, private notification files, earlier authorized downloads and third-party copies are not physically erased by this workflow. Immutable erasure records must be reapplied and reconciled before restoring data to service; an actual restore drill, legal periods, backup expiry and live providers remain release gates. No request is labelled complete account deletion or complete legal erasure. No production erasure is enabled.

Acceptance requires additive schema-014 preservation, strict tenant/subject export boundaries and pagination, independent native-MFA scopes, immutable retries/history, holds, age/state/financial exclusions, proven lock-wait revocation, current lease fencing, atomic rollback/retry, current storefront/canonical-state preservation and accessible native browser workflows. P9.9 costs and unfinished P9.7 cost views remain next.

## Data inventory and retained boundaries

| Category | Owner export | Local primary effect | Retained or unresolved copies |
|---|---|---|---|
| Shops/departments/catalogue | Current allowlisted merchant rows, UUID pages | None | Canonical versions, publication/design/audit history remain |
| Current business contacts | Current structured business fields | None | Immutable contact history, notifications and external published copies remain |
| Invoices | Authorized summaries and net credit only | None | Ledger, reversal, contract/policy and reconciliation history remain |
| Application profile | Requesting applicant's own merchant submissions only | Rejected ≥30 days, no financial references: delete verification byte rows | Application/submission/audit metadata; notification/backups remain |
| Enquiries | Content excluded; request selection includes bounded identity/status/age metadata | Closed ≥30 days: scrub name/reply/message once | Minimal status/retry fingerprint, prior notifications/downloads/backups remain |
| Incidents | Original reporter's own message/owner explanation only | None | Private reviewer notes, contact snapshots and immutable incident history remain |
| Trust/verification investigations | Third-party material excluded | None | Private report/evidence/appeal history retained pending approved legal policy |
| Shop analytics | Retained bounded groups, not raw receipts or identities | Remove shop groups and permanently stop future shop capture | Platform groups, canonical audit events and hashed expiring receipts follow their separate contract |
| Native account/authentication | Excluded | No account deletion | Factors, credentials and session security stay under native mechanisms |
| Privacy requests/holds/events | Only own safe request/status explanations in inventory | No deletion of governance history | Immutable retry/hold/review/erasure receipts needed for restore reconciliation |
| Backups/WAL/platform snapshots/files/external copies | No snapshot/file export | No physical deletion verified | Approved expiry, authoritative post-backup reconciliation and restore drill remain gates |

Public handlers always assign a new/open enquiry with no closure/erasure timestamp. Disposable SQL fixtures explicitly create fictional aged closed records to test time gates; real closure records its server timestamp. Server-only plan HMACs may consider private target content internally to detect change but are never returned in queue, exports, HTML or owner explanations. Requester reason is bounded owner-submitted text rather than a verified identity claim; add no real evidence or credentials.
