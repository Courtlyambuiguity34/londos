# ADR-0008: local reporting, trust review and truthful verification

P9 trust packet, 2026-10-05. This implements local P9.1/P9.2 under the existing loopback/local-adapter boundary. Production moderation policy, legal retention, live escalation/delivery, incident recovery and analytics remain separate plan gates. No report automatically restricts a shop.

Anonymous shop reports use exact origin, bounded JSON, atomic development abuse budgets, a UUID retry key and a browser-generated 256-bit attachment capability. The capability is hashed at rest, never placed in a URL, echoed in responses or exposed to operators. Known and unknown shop IDs receive the same generic receipt; the response contains no shop existence, report identifier or private details. A valid existing target creates one immutable report and one case. Identical retries have no duplicate effect; changed payload/capability under an existing key conflicts. Report content is untrusted text and never enters public rendering, job payloads or merchant responses.

One optional JPEG/PNG/WebP image up to 2 MiB may be attached within 30 minutes, only before any scope claim/decision. Both initial and post-decoding checks require the private capability. Existing secure decoding/pixel/frame/metadata-removal rules produce a normalized WebP; original bytes are discarded. The attachment is immutable, never public and never merchant-readable. Operators need claimed case scope and fresh native MFA to view it. There is no arbitrary remote fetching. Local evidence retention is explicitly provisional pending P9.8; do not ingest real identity/payment documents.

The existing `moderation` operator permission is distinct from review, finance, support, recovery and operations. Default seeds stay unchanged; explicit guarded `db:trust` setup grants the verified fictional review operator and creates/preserves a separate fictional independent reviewer with moderation permission only and no merchant memberships. Private random credentials are retained in ignored files; mismatched existing identities refuse setup rather than reset passwords. Native MFA is still required. Minimal bounded queues reveal category/state/age/priority and shop identity, never report text or capability. A fresh MFA operator claims an audited case scope before any private read or command. Active merchant self-membership denies claim/access. Ownership/support/finance/operations scope never substitutes for a trust-case scope. Recheck current session, grant, scope and self-conflict after merchant-lock waits.

Confirmed decisions compare both case and canonical moderation versions, require private investigation reason and a separate merchant-facing explanation, and atomically commit case state, canonical moderation, shop version, append-only events/audit and private owner notification jobs. Decisions are review, suspend, dismiss or reinstate. Every case contributes its own clear/under-review/suspended restriction. The strongest current restriction across that shop wins; dismissing/reinstating one case cannot clear another. First control captures immutable pre-existing moderation as a baseline. A legacy restriction is preserved, and any external moderation change conflicting with the last computed state fails closed instead of being silently cleared.

Owners with fresh authentication see only redacted own-shop decisions and submit bounded appeals against current case versions. Reporter content, attachment, capability, private investigation notes and operator identity are excluded. An appeal stays pending until a reasoned dismiss/reinstate decision. Clearing a reviewed/suspended case requires a different operator from its last restricting decision; the originating reviewer cannot resolve their own appealed restriction. Merchant restoration never renews rent, removes an operational hold or publishes a draft. All public shop/search/contact/image consumers continue using canonical eligibility, and guest-enquiry intake must use that same rule.

Verification is platform-derived from an approved P8 application, its provisioned shop and private reviewed evidence. Public wording is **“Development application reviewed”**, with a clear statement that this is a fictional local review and not a payment, product or identity guarantee. No merchant-controlled LSS/profile field can create the status; no evidence, applicant fields or report metadata is exposed publicly. Unreviewed shops show no badge. Live verification criteria and claims remain unapproved.

Acceptance requires real PostgreSQL idempotency/concurrency and lock-wait revocation, two merchants, constrained staff, separate operator scopes, immutable private report/evidence/history, native MFA browser workflows, owner redaction/appeal, independent review, multiple-case/legacy restriction preservation, canonical visibility across all consumers, truthful verification, migration preservation and inspected mobile/desktop evidence. A reporting packet does not complete the rest of P9.
