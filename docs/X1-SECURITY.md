## Implemented surfaces

Public fixture mode remains supported. Configured local database mode renders eligible explicitly published canonical shops and shop-first indexed PostgreSQL search. Profile edits alone never publish a layout. Public eligibility requires active publication, active/due/grace tenancy and clear moderation; full shop/search/media reads additionally require a published design pointer. No production provider/CDN eligibility certification is claimed.

Private pages: `/shopkeeper`, `/shopkeeper/shops/[shopId]`, `/shopkeeper/shops/[shopId]/catalogue`, `/shopkeeper/shops/[shopId]/design`, `/shopkeeper/shops/[shopId]/preview`, `/security`, `/landlord`. The separately enabled `/contact/[shopId]` is public, dynamically checks canonical eligibility and exposes only approved contacts; it does not publish private catalogue/media. Account pages: `/sign-in`, `/recover`. The public auth handler is allowlisted; public signup, arbitrary provider paths, trusted devices and passwordless/OTP-only MFA are unavailable. Local bootstrap creates fictional accounts through an explicit guarded CLI; it does not deploy a default administrator password.

Protected domain APIs:

- `GET /api/workspace/shops`, `GET/PATCH /api/workspace/shops/[shopId]`.
- `PUT /api/workspace/merchants/[merchantId]/memberships/[userId]`.
- `POST /api/workspace/merchants/[merchantId]/invitations`, `DELETE .../invitations/[invitationId]`.
- `POST /api/workspace/invitations/accept`.
- `POST /api/workspace/merchants/[merchantId]/ownership`.
- `PUT /api/workspace/merchants/[merchantId]/staff-shops`.
- `GET /api/operator/jobs`, `POST /api/operator/jobs/[jobId]/replay`.
- Under `/api/workspace/shops/[shopId]`: catalogue reads, department/product create/update, contact read/write, private request list/status update and media list/create/upload/retry/delete/ready-variant reads. See [P5 HTTP tests](../tests/e2e-core/p5.spec.ts) for that method registry.
- Design `GET/PUT` and `POST` patch/publish/unpublish/rollback under the same shop scope. [Design HTTP tests](../tests/e2e-core/x2.spec.ts) attack all six methods. Current design/publish grants are distinct; publication also requires fresh authentication and explicit matching-revision confirmation.

P8 adds 22 protected methods, all exercised by [P8 HTTP/browser tests](../tests/e2e-core/p8.spec.ts): owner application list/create/read/edit/submit, private evidence upload/read, application invoices, invoice detail and shop rent/read-renewal; operator review/finance queues, scoped application detail/claim/decision/evidence/invoices, invoice detail/reconcile/reverse and policy list/create. Operators require the action’s current grant and native MFA; private details also require a claimed application scope. Review and finance scopes are separate, including before a shop exists. Sensitive commands and private evidence reads require fresh authentication. Self-review/reconciliation is denied. Finance scope revoked during a merchant-lock wait prevents the waiting credit and leaves no event. Private page authorization runs before HTML/Flight disclosure.

The public guest-request POST still requires exact mutation origin, bounded JSON, opt-in/canonical eligibility, atomic development budgets and idempotency. Image uploads additionally use bounded streamed bytes and owned expiring sessions. Private quarantine and normalized source have no download endpoint; private ready variants require current catalogue/support/design scope. Public ready-image reads independently require current eligibility/published layout/unarchived attachment and never allow normalized source.

New protected APIs must be added to the HTTP attack fixture and authorized again inside their domain service. A server-internal `Actor` is not a browser-provided role or capability. Scope queries and reject missing resources consistently. Operator permission alone must never substitute for tenant scope in support access.

## Transactions and locks

Membership/invitation/ownership/profile/catalogue/contact/request/media/design mutations use the merchant row as the shared serialization point. Recheck permissions after acquiring it. Profile updates compare the supplied canonical version and return 409 on conflict. Write audit and durable work in that transaction. The owner constraint is deferred so an atomic transfer can promote its target before completion. Migration locking/checksums apply separately from runtime command transactions.

Read APIs check grants at request time; mutations recheck after their serialization lock. Operations already authorized at their final check are not promised instantaneous retroactive cancellation. Revocation committed before the next access is tested. Future sensitive reads/writes must define their consistency boundary explicitly. Password reset additionally fences requests already verifying old credentials so they cannot establish fresh authority afterward.

## Operational limits that R1 must retain

- Local adapter files and job payloads can contain live-within-development recovery links/tokens. They are private, ignored and excluded from public handlers. Their production retention/encryption/deletion policy remains open; do not expose them through an operator payload viewer or commit them.
- The PostgreSQL development role is privileged for guarded test database creation. Production least-privilege roles, append-history privileges, database TLS and credential rotation must be implemented/tested before release. Row-level security is not enabled or claimed.
- The rate-limit adapter intentionally uses one loopback network identity and ignores spoofable client IP headers. Atomic account/global budgets are tested. Remote deployment needs a trusted ingress and a reviewed network budget; it is currently blocked.
- `GET /api/ready` requires the current named migration and checks configuration, reporting worker state separately. An offline worker permits browsing/authenticated reads; it leaves durable pending work visible. It does not establish provider readiness or backup health.
- The worker can stop waiting at its deadline. A noncooperative future provider may finish later; its idempotency key and lease-fenced canonical effects are still required. Never describe at-least-once work as exactly-once external delivery.
- X2 implements local private uploads and bounded guest requests with fresh-auth contact changes, audit and local notifications. Production object storage/delivery, ingress/retention policies and operator browser recovery remain open. LSS publication and canonical public discovery now have local P6/P7 evidence with no shared response cache. P8 now verifies scoped application approval and scheduled development rent closure/reopening. Broader moderation/administrative commands, live automatic closure and AI remain later work; current tests do not certify unimplemented consumers.
- This stage tests process/lease recovery. Production backup restoration, disaster recovery, RPO/RTO and safe remote deployment remain P12 requirements.
