## Implemented surfaces

Public fixture mode remains supported. Configured local database mode renders eligible explicitly published canonical shops and shop-first indexed PostgreSQL search. Profile edits alone never publish a layout. Public eligibility requires active publication, active/due/grace tenancy, clear moderation and no operational hold; full shop/search/media reads additionally require a published design pointer. Alias redirects, contacts and ready images recheck the same canonical visibility. No production provider/CDN eligibility certification is claimed.

Private pages: `/shopkeeper`, `/shopkeeper/shops/[shopId]`, `/shopkeeper/shops/[shopId]/catalogue`, `/shopkeeper/shops/[shopId]/design`, `/shopkeeper/shops/[shopId]/preview`, `/security`, `/landlord`. The separately enabled `/contact/[shopId]` is public, dynamically checks canonical eligibility and exposes only approved contacts; it does not publish private catalogue/media. Account pages: `/sign-in`, `/recover`. The public auth handler is allowlisted; public signup, arbitrary provider paths, trusted devices and passwordless/OTP-only MFA are unavailable. Local bootstrap creates fictional accounts through an explicit guarded CLI; it does not deploy a default administrator password.

## Transactions and locks

Membership/invitation/ownership/profile/catalogue/contact/request/media/design mutations use the merchant row as the shared serialization point. Recheck permissions after acquiring it. Profile updates compare the supplied canonical version and return 409 on conflict. Write audit and durable work in that transaction. The owner constraint is deferred so an atomic transfer can promote its target before completion. Migration locking/checksums apply separately from runtime command transactions.

Read APIs check grants at request time; mutations recheck after their serialization lock. Operations already authorized at their final check are not promised instantaneous retroactive cancellation. Revocation committed before the next access is tested. Future sensitive reads/writes must define their consistency boundary explicitly. Password reset additionally fences requests already verifying old credentials so they cannot establish fresh authority afterward.

## Operational limits that R1 must retain

- Local adapter files and job payloads can contain live-within-development recovery links/tokens. They are private, ignored and excluded from public handlers. Their production retention/encryption/deletion policy remains open; do not expose them through an operator payload viewer or commit them.
- The PostgreSQL development role is privileged for guarded test database creation. Production least-privilege roles, append-history privileges, database TLS and credential rotation must be implemented/tested before release. Row-level security is not enabled or claimed.
- The rate-limit adapter intentionally uses one loopback network identity and ignores spoofable client IP headers. Atomic account/global budgets are tested. Remote deployment needs a trusted ingress and a reviewed network budget; it is currently blocked.
- `GET /api/ready` requires the current named migration and checks configuration, reporting worker state separately. An offline worker permits browsing/authenticated reads; it leaves durable pending work visible. It does not establish provider readiness or backup health.
- The worker can stop waiting at its deadline. A noncooperative future provider may finish later; its idempotency key and lease-fenced canonical effects are still required. Never describe at-least-once work as exactly-once external delivery.
- X2 implements local private uploads and bounded guest requests with fresh-auth contact changes, audit and local notifications. Production object storage/delivery and ingress/retention policies remain open; incident-mediated authenticated-owner recovery is now locally verified. LSS publication and canonical public discovery now have local P6/P7 evidence with no shared response cache. P8 now verifies scoped application approval and scheduled development rent closure/reopening. Local scoped reporting/moderation/appeals are now verified; lost-all-factor/email/ownership recovery, analytics/retention/export, live trust policy, financial arrangements, live automatic closure and AI remain later work; current tests do not certify unimplemented consumers.

## P9 assigned incident and recovery extension

Eight protected methods cover owner collection/detail GET/POST, operator queue/detail GET, claim POST and command POST. Anonymous and foreign actors are tested with valid representative bodies, so denials reach authorization. Owner and operator HTML/Flight paths are checked before streaming private data, with private no-store/no-referrer responses. Strict origin, body/schema limits and server-derived reporter identity remain enforced.

Seven incident kinds map to explicit current grants; private access also requires native fresh MFA, current exclusive assignment, a distinct incident scope and no active merchant self-membership. Claims/actions recheck after merchant locks. Escalation clears all scopes/assignment. Proven lock waits test revoked scope/grant, owner membership and native MFA age. Private notes/reviewer identity are excluded from owner history, and report/contact history is excluded from queues/notices/public rendering.

Containment uses the existing R1 generation function plus outstanding native reset-token deletion, targeting only the reporting active owner once per recovery-kind case. Real sessions and old-password in-flight native sign-in are tested; old reset-token use is denied. The existing final authorization boundary remains explicit, without retroactive cancellation claims. Passwords, factors, email, membership and future native login remain unchanged.

Restoration accepts no operator replacement fields. The original active owner freshly confirms the immutable requested snapshot with current case/contact versions; the approval expires after 30 minutes and binds credential generation. Reporter-user and merchant locks serialize approval/restoration against credential changes; a proven user-lock wait with credential rotation denies the restore. Competing restorations have one winner and retain all contact history as new versions. Direct legacy operator contact updates now deny even with recovery/shop scope. Ordinary support has no containment/restoration authority. Lost-all-factor/email/ownership proof remains an unimplemented policy gate.
