ARCHITECTURE DECISION

The previous proposed Django architecture is superseded. Preserve the old ADR as history, but update architecture documentation to record the current decision.

Core:
- Next.js
- TypeScript
- Node.js
- PostgreSQL
- server rendering / React Server Components where appropriate
- minimal client JavaScript
- object storage semantics for media
- background queue/workers for asynchronous work

Node/TypeScript is the primary runtime. Python is NOT required in the normal customer request path. If a future AI/ML/vision workload demonstrably benefits from Python, isolate it behind a worker/service interface rather than coupling public traffic to Python.

PRODUCT CONSTITUTION

Londos is NOT a generic multi-vendor marketplace, Shopify clone, Jumia clone, or website builder.

It is a DIGITAL MALL / DIGITAL COMMERCIAL REAL-ESTATE PLATFORM.

Hierarchy:
Platform -> Mall -> Shop -> Department -> Product/Service

The shop is the fundamental commercial identity. Products belong to shops. Search discovers shops through their contents. A search for "shoes" should surface relevant shops; selecting Annette's shop should enter Annette's relevant shoes context while preserving the ability to browse the rest of her shop.

Businesses rent autonomous digital premises inside Londos. The platform supplies the building, shared discovery, rules, infrastructure and management. Merchants retain their own shop identity and initially control their commerce/contact arrangements.

CUSTOMERS

Never require a customer account merely to browse, search, enter a shop, inspect products, call, open WhatsApp or make an ordinary enquiry. Optional accounts can be added later for convenience.

MULTI-TENANCY

Every shop has an immutable ID such as SHOP-UG-00000451. Names/slugs may change; shop identity must not.

Use a tenant-aware relational model. Do NOT create a database/table per shop.

All shop-owned records must be securely scoped. Every protected server operation must verify actor authorization for the target shop. Add explicit automated attack tests proving Merchant A cannot read or modify Merchant B resources by changing identifiers.

LOGICAL MALLS

Support internal logical malls. Approximately 1,500 shops per logical mall is a planning/operational target, NOT a hard database ceiling. Additional logical malls can be created as capacity grows. Customers normally should not experience infrastructure partitions as "Mall 1/Mall 2". Global discovery spans eligible shops across logical malls, and internal mall assignment must not confer organic ranking advantage.

LONDOS SHOP SPECIFICATION (LSS)

The repository's LSS documents are central.

A shop design is a safe, versioned structured specification, not arbitrary merchant code. Canonical catalogue/business data remains separate from presentation.

Implement the LSS schema, validation and typed component registry. Render only approved components. Existing examples include ShopHero, ShopLogo, Heading, RichText, ProductCard, ProductShelf, DepartmentCard, DepartmentRail, CollectionGrid, PromotionBanner, Image, Gallery, ContactPanel, WhatsAppAction, CallAction, EnquiryAction, PickupInfo, DeliveryInfo, BusinessHours, LocationCard, VerificationBadge and SocialLinks.

Never permit tenant arbitrary JavaScript, arbitrary server code, direct database access, secrets or unrestricted CSS.

Implement bounded theme/design tokens, platform-controlled responsive behavior, accessibility rules and performance budgets.

LSS REVISIONS

Implement:
- working draft
- preview
- immutable published revision
- revision history
- rollback by creating a new revision
- optimistic concurrency/base revision checks

A stale editor must never silently overwrite a newer revision.

CONVERSATIONAL SHOP DESIGN

The merchant-facing Designer should feel like speaking to an interior/shop designer, not programming a website.

Examples:
- "I sell women's clothes and shoes. Make dresses first."
- "Make it elegant."
- "Put new arrivals at the entrance."
- "Move shoes before handbags."
- "Remove the call button."
- "Keep WhatsApp visible."
- "Make this electronics shop feel like a premium showroom."

The pipeline is:
merchant instruction -> authorized context -> structured design intent -> proposed LSS patch -> deterministic validation -> optional AI review/repair -> preview -> merchant confirmation -> immutable revision -> publish -> targeted cache invalidation

AI NEVER directly publishes.

AI NEVER writes arbitrary production React/HTML/JS/SQL.

AI NEVER receives database credentials, deployment credentials, secrets, unrelated merchant data, another shop's private data, unrestricted filesystem access or arbitrary execution capability.

AI PROVIDER ARCHITECTURE

Implement a provider-neutral interface so shop-design logic is not coupled to one vendor. Conceptually:
AIProvider
  -> GeminiProvider
  -> OpenAIProvider

Above providers, implement a LondosDesignOrchestrator.

Use server-side environment variables only. Never expose API credentials to the browser, generated HTML, logs, analytics, error messages or repository. Never commit real keys.

Example configuration names:
GEMINI_API_KEY_1
GEMINI_API_KEY_2
GEMINI_API_KEY_3
GEMINI_API_KEY_4
GEMINI_API_KEY_5
OPENAI_API_KEY

Support multiple Gemini credentials only as a secure credential/failover pool where usage complies with the provider's policies. Do NOT implement key cycling intended to evade quotas, rate limits, billing, restrictions or terms. If a provider reports a quota/rate-limit condition, obey the provider's rules and degrade gracefully rather than deliberately exhausting successive free allowances.

Secrets must be validated server-side at startup/use, redacted from logs, and replaceable without code changes. Use the deployment platform's secret/environment facility in production.

DESIGN ORCHESTRATOR

Do NOT automatically call every model for every edit.

Use the cheapest/simplest safe path.

First perform deterministic Londos checks wherever possible:
- schema
- allowed components
- shop ownership/reference authorization
- supported operations
- component counts
- media/performance budget
- required data
- accessibility rules that can be computed
- revision conflict
- malformed references

Use Gemini as the initial conversational design/planning provider when configured and available. It should return schema-constrained structured intent/LSS patches, not executable code.

OpenAI is a higher-value critic/reviewer/fallback when configured. Use it selectively for cases such as:
- complex redesigns
- low-confidence or ambiguous design
- repeated failed repair
- subjective visual hierarchy/merchandising review
- explicit premium/high-quality review
- configured fallback when appropriate

A simple valid request such as "move shoes above handbags" should not require a paid OpenAI call.

The OpenAI reviewer should inspect the proposed design against merchant intent, LSS rules, mobile usability, hierarchy, merchandising, accessibility and performance, and return structured recommendations/patches. The result must still pass deterministic Londos validation.

Do not assume OpenAI or Gemini output is trusted simply because it conforms to JSON. Treat model output as untrusted input.

AI SAFETY AND PROMPT INJECTION

Treat catalogue text, merchant product descriptions, uploaded text and external content as DATA, never privileged system instructions.

Construct prompts with clear trust boundaries. Only send the minimum authorized shop context required for the task. Prevent cross-tenant context leakage.

Enforce server-side authorization before context is assembled and again before a proposed patch is committed.

Set timeouts, bounded retries/backoff, request size/context limits, per-shop rate limits and usage accounting. Record provider/model, request outcome, latency and usage metadata where available without storing secrets or unnecessarily retaining sensitive prompt content.

If AI is unavailable/quota-limited, existing public shops, search, Shopkeeper ordinary functions, Landlord, rent and commerce must continue. Templates/manual controls remain usable.

Once a design is published, customer rendering uses validated stored LSS and canonical data. Customer visits must generate ZERO AI calls merely to render an existing shop.

AI DESIGN ROLES

Model these as logical responsibilities, not necessarily separate model calls:
- Shop Planner: understands business/departments/customer journey
- Interior Designer: proposes layout/theme/component changes
- Merchandising Assistant: organizes departments/collections/presentation
- Design Inspector: critiques proposed design

Combine roles when that reduces latency/cost without reducing safety. Split only when evidence shows value.

COMMERCE

Allow merchant-configurable approved actions such as:

- call
- enquiry/message
- request/reservation
- COD
- pay on pickup
- Mobile Money after confirmation
- deposit/pre-order instructions

Keep sensitive contact/payment configuration outside arbitrary LSS text; LSS references approved configuration. Do not build a platform wallet or custody merchant funds unless explicitly decided later.

TENANCY / RENT

Implement explicit state machines.

Application:
draft/submitted -> reviewing -> approved | rejected | needs_information

Shop:
provisioning -> unpublished -> active -> temporarily_closed | suspended | archived

Tenancy:
pending -> active -> due -> grace -> closed -> active

Media:
uploaded -> validating -> processing -> ready | rejected | failed

Do not delete shop data immediately when rent expires. Implement reminders, grace, temporary closure and reopening. Closed/suspended shops must be excluded from public discovery according to policy.

Implement an idempotent rent ledger/event model, not merely paid=true/false.

SEARCH

Begin with PostgreSQL-backed search behind a clean search interface so a dedicated engine can later replace/augment it.

Scopes:
- global Londos
- category/department
- shop-local

Search is shop-first. Product matches help rank/surface relevant shops. Prevent one merchant from flooding a results page with duplicate products. Use bounded cursor/pagination; approximately 20 initial results should be configurable.

Exclude non-public/ineligible shops/products. Internal mall assignment must not influence organic rank. Keep any future sponsored promotion explicitly labelled and separate from organic ranking.

PERFORMANCE

Performance is a first-class feature.

Guiding requirement:
"A customer on an ordinary Ugandan mobile connection should never have to download the mall to enter the mall."

Optimize for low-end phones and unstable connections:
- server rendering
- React Server Components where useful
- minimal client components/JS
- code splitting
- bounded queries
- pagination
- lazy media
- responsive optimized images
- cacheable public output
- CDN-friendly design
- targeted invalidation

Do not turn public shops into heavy SPAs unnecessarily.

Track generated HTML, client JS and media bytes. The meaningful metric is how quickly the shop becomes usable on a customer's phone.

CACHING

Public shops are read-heavy. Cache aggressively where correctness permits.

A single product update should:
- commit canonical data
- invalidate only relevant cache
- update relevant search projection/index
- preserve unrelated cached shops

Do not flush the whole mall for one merchant update.

MEDIA

Never deliver raw multi-megabyte merchant phone uploads when optimized variants can be used.

Pipeline:
upload -> validation/quarantine -> metadata stripping/safety checks -> asynchronous processing -> variants -> object storage -> CDN/public delivery

Generate thumbnails/search-card/product-display/compressed high-quality variants. Lazy-load noncritical media. Do not store large media blobs in PostgreSQL.

Failed/delayed media processing must not crash public browsing.

BACKGROUND JOBS

Use a suitable Node-compatible queue/worker architecture for image processing, indexing, analytics aggregation, rent reminders, notifications, scheduled tenancy transitions and future AI jobs.

Jobs must be observable, retryable and idempotent where appropriate. Public storefront requests must not wait for noncritical analytics/jobs.

FAILURE ISOLATION

Design graceful degradation:
- search incident: direct shops should continue where practical
- AI incident: non-AI Londos continues
- analytics incident: storefront continues
- worker backlog: browsing continues
- media processor delay: existing content continues/placeholders where needed
- cache incident: correctness before speed
- database write outage: fail safely; never fabricate successful writes
